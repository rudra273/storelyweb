# E02.1 web settlement and reviewed calculation

New invoices require an explicit full, partial or unpaid choice. Partial amounts are compared as exact integer minor units and must be positive, below the reviewed total, at most two decimal places and within the API payment maximum. Blank, malformed, negative, zero, equal, excess and overprecision input remains visible when refused; no amount is clamped or silently changed.

Changing customer details/type or any payment detail clears unassigned-balance consent. A new authoritative preview, including a settings-only reviewed-context change with the same total, clears the settlement selection and consent while keeping entered amount, method and reference. The existing tabs, layout and theme remain unchanged.

Every fresh request requires the server's `br1:<64 lowercase hex>` reviewed context and sends it with `settlement_choice` (`full`, `partial`, `unpaid`). Missing or unsupported tokens fail closed before draft freezing or network creation. The API checks that context atomically against the calculation/settings snapshot; browser validation alone does not close the preview-to-commit race.

A first fresh `checkout_changed` rejection can release the exact rejected attempt only after durable storage succeeds. It refreshes the preview and requires settlement/consent selection again, retaining other fields. A previously uncertain or restored operation remains frozen after that same response and retains its original body/key. Legacy uncertain bodies without the new paired fields retry unchanged and do not need a fresh preview. Existing E01 storage-before-send and cross-tab protections remain in force.

The next invoice after successful completion starts with settlement unselected. There is currently no web duplicate-sale action to carry a prior settlement. A full persisted checkout lifecycle, held drafts and duplicate-sale workflow remain E02.2 scope; this slice does not claim completion of E02 or human UX acceptance.

## E02.2 — browser checkout recovery and held invoices

The user/shop-scoped v1 draft reader now accepts optional cash, reviewed context and consent context while continuing to read older active-only drafts. Raw checkout amounts, method, reference, cash, customer details, bill type and discount survive reload. Unassigned consent is restored only when the saved customer/payment context and the current server review token agree. A changed token disables creation synchronously before the refresh effect clears settlement/consent; entered fields remain. Legacy uncertain requests bypass these editable review checks and retry their original key/body.

Hold, resume and explicit discard use the same browser Web Lock and record comparison as invoice persistence. Active and held work live in one bounded record, so a transition requires one verified write. Resume atomically swaps meaningful active editable work into the selected held invoice's place. The old store owner retires after a transition; queued stale autosaves cannot recreate an active clone. An uncertain active attempt or malformed/uncertain held entry blocks these actions. Up to 20 held invoices are supported; storage/capacity errors retain the open checkout for explicit retry. A successful invoice clears only active work and keeps held invoices.

Meaningful active or held work does not expire automatically. Discard is explicit. Work stays scoped to the current browser account/shop and reappears after returning to that scope. Explicit signout retains the existing privacy policy of clearing browser drafts. Browser data loss, another device and clients that ignore the locking protocol remain outside this local guarantee; no server draft API was introduced.

Validation covers raw field reload, unchanged-context consent recovery, changed-context renewal, hold/resume swap/discard, failed hold retention, uncertain-operation blocking, concurrent resume ownership, retired autosaves, legacy age recovery, malformed held records and account/shop isolation.
